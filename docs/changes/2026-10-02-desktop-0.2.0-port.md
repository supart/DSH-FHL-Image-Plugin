# Desktop DSH 0.2.0 Port

## Scope

Port `@fhl-plugins/dsh-fhl-image` from the DSH `0.1.1-rc.1` line to the line
shipped by the official DeepSeek Harness desktop application
(`0.2.0-rc.2`), so the same bundle installs through the desktop plugin manager
and keeps registering the three image tools.

Out of scope for this batch: a desktop settings-page client plugin, real image
API acceptance runs, and a refreshed Windows user bundle.

## Why the old package could not be installed on the desktop

- `peerDependencies` declared `^0.1.1-rc.1`. DSH 0.2 evaluates
  `evaluatePluginCompatibility()` (`@deepseek-ai/dsh-app-boot`) against the
  running runtime with `includePrerelease: true`; `^0.1.1-rc.1` means
  `>=0.1.1-rc.1 <0.2.0-0`, which `0.2.0-rc.2` does not satisfy. Installation is
  refused with `incompatible-version`, and startup would skip the bundle.
- `Session.events` was removed in 0.2, and the edit tool's source resolution
  depended on it (`turn/start`, `user/message`, `tool/call`, `tool/result`).

## Changes

- `package.json`: version `0.2.0`; every `@deepseek-ai/dsh*` peer declared as
  `>=0.2.0-rc.2 <0.3.0-0`; added the `@deepseek-ai/dsh-session` peer; dropped
  the unused `@deepseek-ai/dsh-agent` peer and the install-time `prepare`
  script; cordis pinned to `4.0.4`, schemastery to `3.18.4`; added an
  `engines.dsh` declaration (informational — DSH does not enforce `engines`).
- `src/session-images.ts` (new): resolves edit sources from
  `Session.deriveMessages()` (newest user-authored message first, injected
  user-role context skipped) and keeps a bounded, per-session, in-memory
  `ProducedImageMemory` for images this plugin produced. This replaces the
  removed raw-event scans, including the now-dead `tool-result` content block.
- `src/index.ts`: registers tools as before; prompt section moved to order
  `2500` inside the 0.2 tool band; produced images remembered after each
  successful generate/edit; explicit "provide sources explicitly" error kept.
- `cordis.patch.yml`: literal `baseURL` instead of
  `!!js process.env.FHL_IMAGE_BASE_URL`, because a desktop application launched
  from Finder/Start Menu has no shell environment to promise.
- `tsdown.config.ts`: added the new module to the bundle entry list.
- Tests: `tests/manifest.spec.ts` now asserts the peer ranges satisfy
  `0.2.0-rc.2` and that the patch has no `process.env`;
  `tests/session-sources.spec.ts` (new) covers upload precedence, injected
  context filtering, deduplication, unreadable sessions, and cache bounds.
- Documentation rewritten desktop-first: `README.md`, `README-FIRST.zh-CN.md`,
  `docs/INSTALL.zh-CN.md`, `docs/CONFIGURATION.zh-CN.md`,
  `docs/TROUBLESHOOTING.zh-CN.md`, `docs/DEVELOPMENT.zh-CN.md`,
  `docs/SECURITY.zh-CN.md`, `docs/RELEASE_NOTES.zh-CN.md`, `UPSTREAM.md`,

## Operational Note: Re-installing The Same Version

Running the plugin manager's install against a tarball whose package name **and
version** are already installed fails with `application: failed`,
`error.code: "ambiguous-install"`: `pnpm add` succeeds, but the manager cannot
identify which dependency the operation changed, so it never reaches its bundle
validation and enable step. The profile manifest is left intact, but the
extracted `node_modules` copy may stay stale while the lockfile already carries
the new tarball integrity.

To replace an installed artifact, remove first and then install:

```text
plugin_manager { action: "remove_bundle",  target: "@fhl-plugins/dsh-fhl-image" }
plugin_manager { action: "install_bundle", target: "<absolute path to new .tgz>" }
```

Bump the package version for any release that users install over an existing
one.

## Remaining Risk

- The produced-image memory is per host process; after a restart, an edit
  without explicit `sources` reports the documented error instead of reusing a
  pre-restart image. A durable variant would need a host-owned store.
- Only the macOS desktop build was exercised. The Windows desktop path keeps
  the CLI helper script as its documented fallback and is not yet verified.
- The peer ranges accept any future `0.2.x` runtime; a breaking change inside
  the 0.2 line would not be caught by the range check alone. Re-run the manual
  desktop install for each new desktop release.

## Rollback

Revert this batch's files only; the `0.1.0` sources remain recoverable from the
`v0.1.0` tag, and the previously published tag is untouched. To remove the
plugin from the desktop profile, use the plugin manager's remove action.
