# 0.2.2 Client Image Row

Date: 2026-10-08
Branch: `main`
Target: desktop DSH `0.2.0-rc.2`

## Scope

Give the two image-bearing tools a row in the conversation. `0.2.1` shipped the
browser-half omission as an accepted state — its own hardening note recorded
that "this plugin is server-side only and correctly ships no client plugin".
That was correct about the *facts* and wrong about the *consequence*: the images
were reaching the session as durable attachments while the transcript showed
only text, so a user could not see what had been generated.

No tool was added, removed or renamed, and the host half, the credential
references and `cordis.patch.yml` are untouched, so `0.2.2` is a drop-in
replacement for `0.2.1`.

## Root cause, read from the shipped client

Established from the desktop `app.asar`, not from a source checkout:

- The Tool tree dispatches one keyed view per call and falls back to a generic
  card for an unclaimed key: `renderSlot("tool.call.toolview", owner, { entryKey:
  toolName, fallback: <GenericToolCard /> })` (`dsh-client-ui-tool`).
- The generic card's image branch is gated on the built-in tool name:
  `imageCardModel()` returns `null` unless `call?.name === "read_image"`, so
  `fhl_image_generate` and `fhl_image_edit` never reached a gallery.
- The `tool.call.toolview` contract is explicit that any name may be claimed
  ("Any name is allowed, including tools registered by your package … unclaimed
  keys use the generic row"), so claiming the two keys is the supported fix
  rather than a client change.
- The `imageReferences()` admission check the Tool layer applies (non-empty
  `attachmentId`, known image media type, positive `bytes`/`width`/`height`)
  already accepted every field this plugin returns, which is why the images were
  durable but invisible rather than rejected.

## The slot that must not be declared

`tool.call.images` is the Tool-owned gallery slot, and it is declared by exactly
one entry — the built-in read_image view. The registry enforces that at load:

```js
// dsh-client-ui-slots, SlotCore.register
if (options.children) for (const childKey of Object.keys(options.children)) {
  const childRec = this.records.get(childKey)
  if (childRec?.spec) throw new Error(`slot "${childKey}" is already declared (by ...)`)
}
```

Declaring it here would therefore throw while the client loads, so the entries
claim their keys with a bare `{ name, key }` registration and render the
references themselves through the `loadImage` loader the owner supplies.
`tests/ui-bundle.spec.ts` asserts the registration carries nothing beyond
`name` and `key`, which is what keeps a future edit from reintroducing the
declaration and breaking every installation at load.

## Client bundle shape

The client does not load a client half as an ES module. It loads a classic
script that calls `window.__ModuleLoader__.load({ id, factory })`, and the
loader hands that factory the synchronous `require` used for every external
(`dsh-client-modules`). A bare CJS bundle never runs: its top-level
`require`/`exports` are browser globals that do not exist. The browser pass
therefore emits the factory wrapper, and the spec loads the *built artifact*
behind a stubbed `__ModuleLoader__` so the wrapper, the registered id and the
`apply`/`inject` surface are all covered.

React and the other platform seeds stay external because the loader answers them
from the host module table:

```js
// dsh-web-frontend, the boot seed
{ react, "react/jsx-runtime", "react-dom", "react-dom/client",
  "@deepseek-ai/cordis", "@deepseek-ai/dsh-client-store",
  "@deepseek-ai/dsh-client-ui-slots", "@deepseek-ai/dsh-client-ui-primitives",
  "@deepseek-ai/dsh-client-ui-dockkit" }
```

`@deepseek-ai/dsh-client-ui-tool` is **not** in that seed, which is why this
entry imports nothing from it: the contracts it compiles against are declared
locally and its value validation is runtime, so a contract drift degrades to the
generic row instead of failing the client load. No `@deepseek-ai/dsh-client-ui-*`
package is a dependency, and none reaches the published tarball.

## Verification

- `tsc` build pass and `tsc -p tsconfig.test.json` (which typechecks `src/` and
  `tests/` together) both clean.
- 74 tests pass, up from 71: five new cases in `tests/ui-bundle.spec.ts`.
- The new spec renders the registered component through `renderToStaticMarkup`
  with a two-reference result and asserts two `<img>` elements carrying the
  loader's URLs, the envelope text and the prompt, which exercises the gallery,
  the hook usage and the element tree in one assertion.
- `pnpm pack` includes `lib/ui.js`, `lib/types/ui.d.ts` and the `./ui` export
  resolving to an existing file.
- Typecheck, test, build and pack pass on the local Windows checkout.

## Not claimed

- The rendered row has not been observed in a running desktop application. The
  client half loads only at startup, so acceptance needs a full quit and reopen
  followed by a new session; that step is the user's and has no record yet.
- No real image request was made for this change; the renders asserted here are
  `renderToStaticMarkup` output, not provider traffic.
- Cross-platform client loading (macOS, Linux) is unverified.
- `0.2.2` is committed and pushed; no tag or Release asset is created by this
  change, so the public `v0.2.1` tarball still lacks the browser half until a
  release is cut.
